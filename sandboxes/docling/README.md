# Docling Sandbox Prototype

Status: **experimental, isolated, not wired into MIZAN**. Nothing in this folder
touches MIZAN's main repository or any production system.

## Purpose

Evaluate whether [Docling](https://github.com/docling-project/docling) is a
viable **Document Intelligence / Universal Intake** layer for MIZAN, using only
synthetic, non-sensitive data. This is a sandbox, not a replacement for MIZAN's
existing systems.

See the root-level evaluation already on file before reading further:
[`../../evaluations/docling.md`](../../evaluations/docling.md).

## Safety rules followed in this sandbox

1. No real case files, personal data, or legal documents were used anywhere.
   Every fixture in `fixtures/` is synthetic, invented text generated by
   `fixtures/generate_fixtures.py` and clearly labeled "NOT A REAL CASE FILE".
2. No MIZAN production code or repository was modified.
3. All dependencies are installed into an isolated virtual environment
   (`.venv/`, not committed) inside this sandbox folder only.
4. Extraction results are never treated as verified facts — see
   [`adapter.py`](adapter.py) docstring for the
   `SOURCE → EXTRACTED CONTENT → INTERPRETATION → VERIFICATION → ACCEPTED FACT`
   separation this prototype enforces.

## Structure

| Path | Purpose |
|---|---|
| `adapter.py` | `DoclingAdapter` — the only code that imports `docling` directly; everything else should depend on this interface, not on Docling |
| `requirements.txt` | Pinned sandbox dependencies |
| `fixtures/generate_fixtures.py` | Generates all synthetic test fixtures (PDF, DOCX, XLSX, PPTX, Arabic, mixed-language, corrupted, unsupported) |
| `fixtures/*` | Generated synthetic fixtures (regeneratable, not hand-authored binary blobs) |
| `tests/test_docling_adapter.py` | 18 automated tests covering read success, text fidelity, Arabic quality, table extraction, ordering, error handling, determinism, performance, provenance |
| `benchmark/RESULTS.md` | Actual measured results from running the tests on this machine, including the Arabic normalization finding and performance numbers |
| `benchmark/pytest_raw_output.txt` | Raw pytest console output for this run |
| `COMPARISON_AND_DECISION.md` | Final REUSE/EXTEND/CONNECT/INSPIRE/REJECT decision with reasoning |

## How to reproduce

```powershell
cd sandboxes\docling
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
.\.venv\Scripts\python fixtures\generate_fixtures.py
.\.venv\Scripts\python -m pytest tests -v
```

First run will download ~30MB of OCR models and a layout model from the
internet (see `benchmark/RESULTS.md` §8) — this requires network access once;
subsequent runs are cached locally.

## Headline result

18/18 automated tests passed. The most important finding is **not** "it
works" — it's that Arabic text extraction requires an explicit NFKC
normalization step to be usable, and that the default pipeline is ~3x slower
than necessary for born-digital PDFs because OCR runs unconditionally. Both
are documented with reproducible evidence in `benchmark/RESULTS.md`.

## Final decision

See [`COMPARISON_AND_DECISION.md`](COMPARISON_AND_DECISION.md) for the full
reasoning. Headline decision: **EXTEND** — Docling is adopted as an isolated,
adapter-wrapped ingestion service for born-digital and scanned documents, with
mandatory NFKC normalization and explicit OCR-mode configuration layered on
top by MIZAN, not accepted as-is.
